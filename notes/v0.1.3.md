UX hardening de la pantalla de Actualizaciones + fix del AP propio.

- feat(panel): overlay full-screen "Actualizando dispositivo" mientras `anna-update-apply.sh` reinicia el server. Polling adaptativo 3s/8s y auto-recarga cuando vuelve el server con la nueva versión.
- fix(server): `GET /api/admin/device/updates` filtra `pending` por comparación semver — si una fila `status='downloaded'` está en BD para una versión <= actual (residuo de installs antiguos fallidos), ya no aparece como "lista para instalar".
- fix(panel): banner rojo "Última actualización con incidencia" solo se muestra cuando la entrada más reciente del historial es un fallo, no cuando hay cualquier fallo histórico ya superado.
- feat(server): `GET /api/admin/device/updates` devuelve `installing: { version }` cuando hay una fila `status='applying'` (espejo del endpoint del kiosk).
- fix(pi): AP propio (`anna-ap`) ahora vive en interface virtual `ap0` creada al boot por `anna-ap-iface.service`, en lugar de competir con la STA externa por `wlan0`. Antes el AP simplemente no aparecía en la lista de redes si había WiFi externo configurado. Defensive: si el chip wifi no soporta interface virtual (Pi 3B v1.2 con firmware antiguo, adaptadores USB), el unit loguea warning y el AP solo funciona si se desconecta la STA.

**Paso manual post-instalación** (UNA vez por Pi ya provisionada con v0.1.x anterior, similar al splash Plymouth de v0.1.2):

```bash
ssh -t admin@<host> 'sudo bash /opt/anna/current/scripts/pi/bin/anna-enable-ap-iface.sh'
```

Tras este paso, el SSID del AP debería aparecer en la lista de redes WiFi cercanas. Si el script termina con código 2, el chip wifi de esa Pi no soporta AP+STA simultáneo y el AP solo estará disponible cuando la STA externa esté desconectada.
